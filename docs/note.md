# 実装メモ（詰まったところと判断の記録）

## 詰まったところ

| 症状 | 原因 | 対処 |
|---|---|---|
| `No module named pytest` | 仮想環境に pytest がない | `.venv` を作って有効化し、`python -m pip install pytest` |
| `python -m .\tests\test_data.py` が失敗 | `-m` にはファイルパスではなくモジュール名を渡す | `python -m pytest tests -q` で実行する |
| 分割のテストで個数が 1 ずれる | `1 - 0.8 = 0.19999999999999996` で、`int(49 × 0.2)` が 9 になる | テストの個数は「全体 − 訓練」で書く |
| `'list' object has no attribute 'tolist'` | `tokens.tolist()` の要素はすでにリスト | テンソルの段階で `tokens[:, :2]` を切ってから `.tolist()` |
| `No module named 'grokking.analysis'` | `analysis/__init__.py` と `neurons.py`（`capture`）がまだなかった | 空の `__init__.py` と `capture` を先に作る |
| パラメータ数のテストが 1568 で失敗 | テスト用の小さいモデルで数えていた | `Config()` の基準設定で作ったモデルで数える（226,048） |
| GIF の1コマが 0 ms になる | imageio 2.37.3 の `mimsave` は `duration` をミリ秒で受け取る | `duration=300`（ミリ秒）で渡す |
| `git add` で LF/CRLF の警告 | Windows の改行コードの自動変換 | 動作に影響しないので、そのまま進める |

## 型チェッカー（Pylance）の警告

| 警告 | 原因 | 対処 |
|---|---|---|
| `int` に `item` がない | `sum()` は整数 0 から足し始めるので、結果が `int` かもしれない | 各要素で `.item()` してから合計する |
| `tuple[float, ...]` を `tuple[float, float]` に割り当てられない | `tuple(リスト)` は要素数が型に現れない | `beta1, beta2 = self.betas` で取り出して組み直す |
| `Module` に `__getitem__` がない | `register_buffer` の名前は `nn.Module.__getattr__` 経由で `Tensor \| Module` になる | クラスの先頭で `mask: torch.Tensor` と宣言する |
| `Tensor \| Module` を `Tensor` に渡せない | 引数を `nn.Module` と型指定していた | `Callable[[], Transformer]` にする（`TYPE_CHECKING` で import） |

## 設計上の判断

| 判断 | 理由 |
|---|---|
| `Transformer` の既定値を消し、`Config` に一本化 | 引数の渡し忘れがエラーにならず、記録と実体がずれるのを防ぐ |
| `Config` の既定値も消し、値は `base.json` だけに書く | 同じ値が2か所にあると、片方だけ直したときにずれる。キーの書き忘れも既定値で黙って埋めずにエラーにする。後でキー（実験 F の `init_scale` など）を足したら、それ以前の `runs/*/config.json` は `Config.load(path, init_scale=1.0)` のように足りないキーを明示して読む |
| `seq_len` を `Config` に入れない | 系列長はデータ `[a, b, =]` が決める。食い違いを構造的に防ぐ |
| `config.json` に git ハッシュを書く | どのコードの結果かを辿れる。`Config.load` はこのキーを読み飛ばす |
| 出力先が空でなければ止める | 同じ `run_name` で再実行すると、古いチェックポイントが混ざる |
| `capture` の hook は値を返さない | forward hook は `None` 以外を返すと出力を置き換える。`lambda` で `setdefault` の値を返すと、2回目以降の出力が1回目の値に化ける |
| 解析の関数に `@torch.no_grad()` | `requires_grad` のテンソルは `.numpy()` できない。呼び出し側の `detach` 忘れでも壊れない |
| MLP のバイアス、`W_out`・`W_U` の初期化、出力の次元（p + 1）、ウォームアップを公開実装に合わせる | 実装ガイドは解析を素直にするためにバイアスを省き、初期化を fan_in でそろえていた。元論文の結果と同じ条件で比べられるよう、公開実装に合わせた。解析では `W_U[:p]` を使う |
| 損失を float64 で計算 | float32 の `log_softmax` は、自信の強い予測で損失を約 1.2e-7 の倍数に丸める。構造を変えずに精度だけを比べると、float32 だけで訓練損失が繰り返し跳ねた（下の「損失の精度の比較実験」） |

## 損失の精度の比較実験（CPU、40,000 ステップ）

損失の精度（float32 / float64）だけを変えて学習し、比べた。設定は `configs/base.json`、`data_seed = init_seed = 0`、CPU で各1回（実験1は 2 スレッドずつ2本を並列、実験2は 4 スレッドで1本ずつ）。float32 の学習は、`grokking.train.cross_entropy` を `F.cross_entropy` に差し替えて回した。

| 実験 | 構造 | ステップ数 | 所要時間 | float32 のスパイク | float64 のスパイク |
|---|---|---|---|---|---|
| 1 | 公開実装に合わせる前 | 4,000 | 約 510 秒 | 2 回（1,720、3,110 付近、最大 0.015） | なし |
| 2 | 公開実装に合わせた後 | 40,000 | 4,819 秒 / 5,436 秒 | 30 回（1,700〜39,800、間隔 1,200〜1,400、最大 0.079） | なし |

実験2の比較：

| 項目 | float32 | float64 |
|---|---|---|
| テスト精度が 0.1 / 0.5 / 0.99 を超えるステップ | 1,800 / 4,700 / 5,700 | 2,100 / 4,800 / 5,700 |
| 汎化した後に 0.99 を下回った回数と最小値 | 3 回（5,900、21,400、27,900）、0.962 | 0 回、0.990 |
| 重みの二乗和（200 / 4,000 / 10,000 / 40,000） | 3,644 / 3,158 / 1,090 / 1,119 | 3,656 / 2,381 / 947 / 912 |
| `W_E` の上位5周波数 | 44, 6, 30, 16, 32 | 44, 16, 6, 20, 40 |
| `W_L` の上位4周波数 | 30, 16, 44, 6 | 44, 20, 16, 6 |

float64 で学習した重み（実験2）から、float32 と float64 の両方で訓練データ全体の勾配を計算し直し、比べた。

| ステップ | 平均損失 | float32 で損失がちょうど 0 になる組の割合 | cos(float32 の勾配, float64 の勾配) |
|---|---|---|---|
| 1,534 | 3.5e-7 | 2% | 0.97 |
| 4,550 | 2.4e-7 | 14% | 0.94 |
| 7,835 | 1.0e-7 | 60% | −0.21 |
| 40,000 | 9.5e-8 | 63% | −0.51 |

分かったこと：

- 振動の原因は損失の精度で、モデルの構造ではない。構造を変えても、float32 なら同じように跳ねた。
- 正解の確率 1 − ε のうち ε が約 6e-8 刻みに丸められ、正解クラスの勾配だけが不正確になる。損失が 1e-7 前後になると、float32 の勾配は正しい勾配とほぼ無関係か、逆向きになる。
- float32 では、スパイクの間に重みの二乗和が weight decay に逆らって増え、スパイクで急に下がる。Adam が勾配の大きさを正規化するので、丸めで偏った小さな勾配も、学習率いっぱいの一歩になるためと考えられる（推論。勾配のスナップショットしか見ていない）。実験1でも、float32 では跳ねる直前に二乗和の減りが止まり（3,146 → 3,140）、跳ねた後に急に減った（80 ステップで 3,107 → 2,686）。
- 汎化する時期はほぼ変わらない。振動は grokking に必要でも、grokking を妨げるものでもない（実装ガイドの「跳ねても grokking は起きる」と一致）。
- float32 では、汎化した後もテスト精度が一時的に下がり、学習の終わりに使う周波数も変わる。README の図1〜3（float32 の版）の周波数を、新しい版と比べるときは注意する。
- 限界：シード1つ、各1回、CPU の結果。訓練データの選び方は公開実装と違う。
